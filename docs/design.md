# ticket-hub 设计文档 v1（工单同步与多渠道提醒）

> 状态：待评审。评审通过前不写业务代码。

## 1. 目标与范围

- 从上游「字节跳动 IDC 供应商门户（Dora）」https://idc-service.bytedance.com/ 同步工单，**只同步与提醒**，不在本系统里认领、处理、结单，也不回写上游。
- B/S 架构，PC 浏览器与手机 H5 同一套响应式前端。
- 角色：超级管理员、普通用户。
- 规模：≤50 用户，≤1000 工单/天；目标是**新工单出现到提醒送达 ≤ 1 分钟**，常态 10~30 秒。

不做：上游自动认领/审批/结单、多租户、原生 App。

## 2. 上游现状（调研结论）

### 2.1 登录
- 当前登录页同时有 `Email`、`SMS` 两个验证码登录标签，未见图形验证码/滑块（发码后的风控分支未验证）。
- 登录走 IAM（`dora.iam.bytedance.com`，OIDC 授权码回调到 `idc-service.bytedance.com/accounts/login/`），登录 SDK 的接口：
  - 发码：`POST /api/v1/login/sms`，体 `{account, account_type:"email", scene:"login"}`，返回流程 `token`
  - 验码：`POST /api/v1/login/account/code`，体 `{code, token, account_type}`
- 会话：Cookie + `csrftoken` / `X-CSRFToken`。业务会话 Cookie 名、有效期、业务 XHR 鉴权方式**尚未确认**（需要用真实账号登录一次抓包）。
- 验证码"比较慢"，有效期 10 分钟。

### 2.2 工单类型
公开手册里带"待认领 / 待我处理"的接单型模块（IT 运维管理下）：故障维修、服务器下架、服务器改配、物流、机房/服务器巡检、机柜操作工单、协查、入室、事故复盘；基础设施侧另有机柜上下电、安全工单、事件、维护、变更等（后几类手册已迁到登录后文档中心，字段未知）。

**很多模块上游本身会给供应商邮箱发"待认领"邮件**（下架、物流、改配、巡检、故障维修、机柜操作），这是提速的关键（见 4.3）。

### 2.3 待确认（阻塞上游采集实现）
1. ~~工单类型~~：已定为**全部同步**。按上游菜单逐类实现 Collector，先做有"待认领"邮件的接单型模块，再做基础设施侧模块。
2. 一个可登录的上游账号邮箱 + 该邮箱 IMAP 授权码，用来抓业务列表/详情接口。
3. 该邮箱是否就是上游发"待认领"通知的收件邮箱。

## 3. 总体架构

```
            ┌──────────── 浏览器 (PC / H5) ────────────┐
            │   React + Vite + Ant Design（移动端 antd-mobile 适配）│
            └──────────────────┬──────────────────────┘
                               │ REST + SSE(站内实时)
┌──────────────────────────────▼───────────────────────────────┐
│ ticket-hub 单体服务（Go + Gin + GORM）                          │
│  api          鉴权、用户、配置、工单查询、订阅                  │
│  upstream     上游会话管理（发码→IMAP取码→登录→保活）、采集器    │
│  mailwatch    IMAP IDLE 监听：①登录验证码 ②上游通知邮件触发     │
│  syncer       轮询调度、增量对比、生成事件                      │
│  notifier     规则匹配 → 渠道发送（短信/邮件/企微/飞书/站内）、重试 │
│  scheduler    定时任务（Redis 锁防重，可多实例）                 │
└──────┬──────────────────────────────────────────────┬────────┘
       │ GORM / go-redis                               │ 出站
  SQLite（本地调试） / PostgreSQL（生产） + Redis     上游 Dora、IMAP、SMTP、阿里云短信、企微/飞书 Webhook
```

- 单二进制 + 内嵌前端静态文件，Docker Compose（app + postgres + redis）部署；本地 `DB_TYPE=sqlite` 一条命令跑起来。
- 引入 Redis：缓存（配置、用户会话/JWT 黑名单、工单列表热点查询、上游会话 Cookie 副本）、分布式锁（同一采集器/登录流程只跑一个）、发送限频计数（企微/飞书/短信）、通知队列（Redis Stream，`notify_jobs` 表作持久记录与重放）、SSE 跨实例广播（Pub/Sub）。
- Redis 只放可重建数据，丢了从 DB 恢复；本地调试可用 `REDIS_URL` 为空时退化为进程内实现（内存缓存 + 本地锁 + channel 队列）。
- 两种数据库都支持：只用 GORM 通用能力，不写方言 SQL；JSON 字段用 `TEXT` 存，CI 里两种库都跑测试。

## 4. 上游同步

### 4.1 会话管理（UpstreamAccount）
状态机：`未登录 → 发码中 → 等待验证码 → 登录中 → 在线 → 过期/失败`

1. 调发码接口（账号 = 配置的邮箱）。
2. `mailwatch` 在该邮箱 IMAP 上等待新邮件（按发件人 + 主题正则过滤，正则可在后台配），用正则提取验证码（默认 `\b\d{6}\b`，可配），超时 10 分钟。
3. 调验码接口，完成 OIDC 跳转，保存 Cookie Jar（加密落库）。
4. 保活：每 N 分钟请求一个轻量接口；收到 401/跳登录页即判定过期，自动重走 1~3。连续失败 ≥3 次停止自动重试并告警管理员（防止触发上游风控/频繁发码）。
5. 后台提供「手动登录」：管理员可手填验证码，兜底 IMAP 不可用的情况。

> 如果抓包确认登录必须执行前端 JS（签名、指纹、滑块），改为在服务内用 headless Chromium（chromedp）完成登录拿 Cookie，采集仍走 HTTP。两种实现放在同一个 `Authenticator` 接口后面。

### 4.2 采集器（Collector）
每类工单一个 Collector 插件，统一接口：

```go
type Collector interface {
    Kind() string                                  // 如 "fault_repair"
    List(ctx, sess, since time.Time) ([]RawTicket, error) // 列表增量（含待认领 + 待我处理）
    Detail(ctx, sess, id string) (RawTicket, error)
    Normalize(RawTicket) Ticket                    // 映射到统一模型
}
```
- 优先调上游页面自己用的列表/详情 XHR；没有可用 XHR 才退化为页面解析。
- 列表要同时拉"全部/待认领"和"我的/待我处理"，避免漏掉未认领工单。
- 每次同步后，用 `upstream_id + kind` 去重；对比关键字段（状态、当前节点、处理人、截止时间）的哈希，变化才生成事件：`ticket.created` / `ticket.status_changed` / `ticket.updated`。
- 原始 JSON 保留（`raw`），方便后续加字段不重拉。

### 4.3 怎么做到"尽快收到"
两路并行：
- **邮件触发（快路径）**：IMAP IDLE 监听上游通知邮件（"待认领"等），收到即对对应模块立刻触发一次同步，通常数秒内出结果。
- **定时轮询（兜底）**：每类工单默认每 30 秒轮询一次（可配 10s~10min），工作时间/非工作时间可设不同频率。1000 单/天的量，对上游的压力可以忽略。
- 上游限流或报错时指数退避，并在后台显示"最后成功同步时间"。

## 5. 数据模型（主要表）

| 表 | 说明 |
|---|---|
| `users` | 账号、密码哈希(bcrypt)、角色 `admin/user`、手机号、邮箱、企微/飞书 @ 标识、启用状态 |
| `settings` | KV 配置（站点名、Logo、登录策略等），值为 JSON |
| `upstream_accounts` | 上游登录邮箱、IMAP 配置引用、会话 Cookie（加密）、状态、最后登录时间 |
| `mail_accounts` | IMAP / SMTP 账号（主机、端口、TLS、用户名、授权码加密），用途标记 |
| `channels` | 通知渠道实例：`sms_aliyun / email / wecom_bot / feishu_bot / inapp`，配置 JSON（密钥加密），启用状态 |
| `collectors` | 每类工单：启用、轮询间隔、过滤条件（机房/园区等） |
| `tickets` | 统一工单：`kind, upstream_id, title, status, node, site(机房/园区), assignee, priority, deadline, created_at_upstream, updated_at_upstream, raw` |
| `ticket_events` | 变更事件：类型、前后值、时间 |
| `notify_rules` | 管理员规则：条件（工单类型/状态/机房/关键词/事件类型）→ 动作（通知哪些用户/群、用哪些渠道、模板） |
| `subscriptions` | 普通用户订阅：关注的工单类型/机房、接收渠道、免打扰时段、紧急事件是否突破免打扰 |
| `notify_jobs` | 待发/已发记录：渠道、目标、内容、状态、重试次数、错误信息（也作为发送日志） |
| `audit_logs` | 管理操作审计 |

所有密钥类字段用 `APP_SECRET_KEY`（环境变量）做 AES-GCM 加密落库，接口只回显打码值。

## 6. 提醒

### 6.1 流程
`ticket_event` → 匹配 `notify_rules`（管理员）和 `subscriptions`（用户）→ 按"用户 × 渠道"去重 → 免打扰/频控检查 → 写 `notify_jobs` → worker 发送，失败按 1s/10s/60s/5min 重试 4 次。

### 6.2 渠道
| 渠道 | 实现 | 备注 |
|---|---|---|
| 阿里云短信 | 官方 Go SDK `dysmsapi`，配置 AccessKey、签名、模板 Code、模板变量映射 | 模板需先在阿里云审核；短信费用，默认只对新建/紧急事件发 |
| 邮件 | SMTP（TLS/STARTTLS），HTML 模板 | 与 IMAP 账号分开配置 |
| 企业微信 | 群机器人 Webhook，markdown 消息，可 @手机号 | 每机器人 20 条/分钟限频，worker 内按 Webhook 限速 |
| 飞书 | 群机器人 Webhook，支持签名校验，卡片消息 | 100 次/分钟、5 次/秒限频 |
| 站内 | DB + SSE 推送，H5/PC 页面角标与列表 | 永远发，作为兜底 |

模板用 Go `text/template`，变量如 `{{.Ticket.Title}} {{.Ticket.Status}} {{.Link}}`，后台可编辑并"发送测试"。

### 6.3 用户侧
普通用户在「我的提醒」里：选择要关注的工单类型/机房、勾选渠道（只有管理员已启用的渠道可选）、免打扰时段、绑定手机号/邮箱；企微/飞书群机器人是群维度，由管理员配置，用户只能选择"我关注的消息在群里 @我"。

## 7. 管理后台（超级管理员）
- 站点设置：名称、Logo、对外访问地址（用于消息里的链接）、登录方式、会话时长。
- 用户管理：增删改、重置密码、禁用、角色。
- 上游配置：上游登录邮箱、IMAP、验证码邮件过滤规则与提取正则、手动登录、会话状态、立即同步。
- 采集配置：启用哪些工单类型、轮询间隔、过滤条件、最后同步时间与错误。
- 渠道配置：SMTP、阿里云短信、企微/飞书机器人（可多个），每个都有"发送测试"。
- 提醒规则 & 模板。
- 日志：同步日志、发送日志（可重发）、审计日志。

## 8. 前端
- React + TypeScript + Vite；PC 用 Ant Design，移动端按断点切换布局（列表卡片化、底部 Tab），不维护两套页面。
- 页面：登录、工单列表（筛选：类型/状态/机房/时间/关键词）、工单详情（含变更时间线、上游原文链接）、我的提醒、站内消息；管理端见第 7 节。

## 9. 安全
- 本系统登录：账号密码 + bcrypt，JWT（HttpOnly Cookie），登录失败限次；首次启动用环境变量创建超级管理员。
- 密钥加密存储（第 5 节），日志脱敏。
- 只读访问上游，不提供任何回写上游的接口。
- 上游账号是你们公司在门户的真实账号：采集频率、并发都设上限，避免触发风控。

## 10. 部署与开发
- `docker compose up -d`：app + postgres + redis；数据卷持久化。
- 本地：`DB_TYPE=sqlite DB_DSN=./data.db go run ./cmd/server` + `pnpm dev`。
- 配置：环境变量只放启动必需项（DB、`APP_SECRET_KEY`、监听端口、初始管理员），其他都在后台配置。
- CI：GitHub Actions 跑 `go test`（SQLite + PostgreSQL 两套）、前端 lint/build、构建镜像。
